## Журнал проблем

---

### 1. Подключение приложения к PostgreSQL: WinError 64 и «password authentication failed»

**Контекст:** FastAPI + async SQLAlchemy 2.0 + Alembic, PostgreSQL поднимался в Docker Compose (`postgres:16-alpine`), локально разработка велась на Windows с Python 3.14.6 в venv. Проект переходил на новую схему (таблица `users`, связь 1:N с `tasks`) и нужно было применить миграции Alembic.

---

#### 1.1 Симптом

Команда `python -m alembic current` (и любые другие, обращающиеся к БД) падала с ошибкой:

```
OSError: [WinError 64] Указанное сетевое имя более недоступно
ConnectionResetError: [WinError 64]
asyncpg.exceptions.ConnectionDoesNotExistError: connection was closed in the middle of operation
```

При этом:
- `python -m alembic history` работала нормально (она читает только файлы миграций с диска и не подключается к БД);
- контейнер БД был `Up (healthy)`, порт `0.0.0.0:5432->5432/tcp` проброшен;
- проверка изнутри контейнера (`docker compose exec db psql ...`) проходила успешно.

---

#### 1.2 Диагностика (пошагово)

1. **История vs current.** Выяснил, что `history` не трогает сеть → ошибка именно на этапе сетевого соединения.
2. **Состояние Docker:** `docker compose ps` → контейнер `Up (healthy)`, порт проброшен.
3. **Логи PostgreSQL в контейнере** (`docker compose logs db`) → база готова, но **нет вообще ни одной записи о входящих подключениях** — трафик до контейнера не доходил.
4. **Проверка TCP из Windows:** `Test-NetConnection 127.0.0.1 -Port 5432` → `TcpTestSucceeded True`; `socket.create_connection(('127.0.0.1', 5432))` → успешно. Значит, порт слушается.
5. **Прямой тест драйверов** через маленький скрипт:
   - `asyncpg.connect(...)` → WinError 64;
   - `psycopg.connect(...)` → **`password authentication failed for user "postgres"`** — уже другая, осмысленная ошибка! Драйвер реально дошёл до сервера и получил отказ.
6. **Ключевой шаг — `netstat -ano | findstr :5432`:** порт 5432 слушают **два процесса**:
   - `postgres.exe` (PID 6056) — **локальный PostgreSQL, установленный в Windows** как служба;
   - `com.docker.backend.exe` (PID 19392) — прокси портов Docker Desktop.
7. **`tasklist /FI "PID eq ..."`** подтвердил: локальная служба PostgreSQL тоже занимает 5432 и перехватывает входящие соединения.

---

#### 1.3 Причина (корень)

Было **две независимые причины**, наложившиеся друг на друга:

**А. Конфликт портов 5432.** На хосте одновременно слушали порт два PostgreSQL:
- локальная служба Windows (сервер «Sokol», русская локаль сообщений — отсюда русские тексты ошибок);
- Docker-контейнер.

Windows направляет входящие соединения на один из слушателей, и трафик уходил в **локальный** PostgreSQL, у которого другой пароль. Поэтому:
- psycopg честно получал «password authentication failed»;
- логи Docker-контейнера оставались пустыми.

**Б. asyncpg 0.31.0 несовместим с Python 3.14 на Windows.** Даже после устранения конфликта (прямое подключение к локальному PG с правильным паролем) asyncpg продолжал падать с WinError 64 на этапе чтения ответа сокета через ProactorEventLoop — ошибка возникала **до** стадии аутентификации. То есть дело было не только в неправильном сервере, но и в самом драйвере.

Дополнительный нюанс: **psycopg в async-режиме не работает с ProactorEventLoop** на Windows — требует SelectorEventLoop.

---

#### 1.4 Решение

1. **Отказались от Docker-базы** — проект переведён на локальный PostgreSQL (сервер Sokol):
   - `docker compose down -v` (удалены контейнер, сеть, volume);
   - `.env`: `DB_HOST=127.0.0.1`, `DB_PASSWORD=...` (реальный пароль локального PG), `DB_NAME=task_manager` (база создана скриптом через `CREATE DATABASE`).
2. **Сменили драйвер asyncpg → psycopg** (psycopg3):
   - `core/config.py`: URL `postgresql+psycopg://` вместо `postgresql+asyncpg://`;
   - `requirements.txt`: `psycopg[binary]==3.3.6` (бинарное колесо под cp314 существует → поддержка Python 3.14);
   - пакет поставлен через `pip install "psycopg[binary]"`.
3. **Адаптировали event loop под psycopg на Windows:**
   - `alembic/env.py`: миграции запускаются на явном `asyncio.SelectorEventLoop(selectors.SelectSelector())` (чистый способ, без deprecated API);
   - `database.py`: на Windows задаётся `asyncio.set_event_loop_policy(asyncio.WindowsSelectorEventLoopPolicy())` (deprecated с 3.14, удалят в 3.16 — в долгосрочной перспективе лучше перейти на другой подход, но для текущей версии работает).
4. **Проверка результата:**
   - `python -m alembic current` → подключение к PostgreSQL прошло;
   - `python -m alembic upgrade head` → применены обе миграции;
   - `python -m alembic check` → `No new upgrade operations detected` (модели = БД).

---

#### 1.5 Как рассказать на собеседовании (короткая версия)

> «Во время миграций Alembic столкнулся с WinError 64 и ошибками аутентификации. Пошагово локализовал: история миграций работает (не трогает сеть), а команды с подключением — нет. Проверил Docker (контейнер healthy, порт проброшен, но в логах ноль подключений), затем netstat показал, что порт 5432 слушают два процесса — локальная служба PostgreSQL и Docker-прокси; трафик уходил в локальную БД с другим паролем (отсюда русский текст “password authentication failed” у psycopg). После устранения конфликта выяснилось, что asyncpg 0.31.0 вообще несовместим с Python 3.14 на Windows — падает ещё до аутентификации. Решил переходом на psycopg, адаптировал event loop для Windows (SelectorEventLoop) и перенёс проект на локальный PostgreSQL. Итог: миграции применяются, check показывает полную синхронизацию схемы.»

---

#### 1.6 Уроки / что это дало

- **Диагностика сетевых проблем:** разделять «слой» проблемы — файлы (история миграций), TCP-слой (netstat, Test-NetConnection), слой приложения (драйвер, пароль).
- **Не доверять одному драйверу:** asyncpg падал с непонятной сетевой ошибкой, а psycopg дал точный текст от сервера — смена инструмента помогла локализовать причину.
- **Один порт — разные сервисы:** на Windows часто стоит локальный PostgreSQL, конфликтующий с Docker-пробросом портов.
- **Версии Python важны:** свежий Python (3.14) может быть раньше бинарных колёс/поддержки в драйверах — проверять совместимость при выборе библиотек.
- **Alembic autogenerate не всё видит:** server_default и CheckConstraint пришлось добавить в миграцию вручную.
